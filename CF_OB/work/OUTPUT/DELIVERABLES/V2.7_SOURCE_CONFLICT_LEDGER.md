> Per PROMPT §7: for every meaningful conflict between source documents (Tier 1/2
> latest requirements vs older 2/3-button mockups and superseded behavior), record
> topic, sources, old vs required behavior, decision, why, and implementation impact.
> Resolved once, then implemented against the resolved ledger.

## C01 — Number of UI buttons: 3 vs 4

| Field | Value |
|---|---|
| Source A (old) | Older mockups: 2-button, then 3-button (`ULTRA_DETAIL` §Q9 asks "đúng 3 nút"). |
| Source B (latest) | User roadmap Bước 8 + `ALL_IN_ONE` §86: **4 buttons**. |
| Old behavior | CHECK and load folded together; no explicit reset. |
| Required behavior | 4 buttons: 1.TẢI WH / 2.CHECK / 3.XỬ LÝ / 4.LÀM MỚI. |
| Decision | **4 buttons.** |
| Why | Roadmap is newest authority; a distinct LÀM MỚI is needed to invalidate a stale plan lock without touching SAP or history. |
| Impact | New entry point `CF_ResetUI` (`modCFResetUI`); hide 3 diagnostic buttons; keep 3 existing flow macros. Physical shape layout deferred (cosmetic). |

## C02 — CHECK + EXECUTE merged vs separated

| Field | Value |
|---|---|
| Source A (old) | Single combined "check-and-execute" mental model. |
| Source B (latest) | Roadmap Bước 3: CHECK read-only, XỬ LÝ executes only a locked, fingerprinted PlanID. |
| Old behavior | FAST executor could write SAP without verifying CHECK's plan lock (Seam 2 hole). |
| Required behavior | CHECK never writes SAP; EXECUTE refuses unless the plan lock + hashes match. |
| Decision | **Separated, enforced by lock.** |
| Why | Non-negotiable safety invariant; prevents executing a stale/re-derived plan. |
| Impact | FAST path `CWR_RunFastToCFCore` now calls `CWR_AssertQueuePlanLock` BEFORE create (lock@1300 < create@1318). Additive reuse of the existing guard — no new infra. |

## C03 — 20 sheets vs 5 sheets

| Field | Value |
|---|---|

| Source B (latest) | Roadmap Bước 7 + REDESIGN §: 5 canonical sheets (INPUT / DATA_CORE / PLAN / SYSTEM / RUN_HISTORY). |

## C05 — Old P-loop vs group scheduler

| Field | Value |
|---|---|
| Source A (old) | Per-P (per-document) sequential loop reopening MON per member. |
| Source B (latest) | REDESIGN §: phase-ordered group scheduler + member allocation ledger. |
| Old behavior | GROUP_DELTA=0 → `PRDO_QTY_ALREADY_TARGET|NO_QTY_WRITE` → lost member Creates (the net-zero bug). |
| Required behavior | CONTRACT_A (PRDO aggregate) AND CONTRACT_B (per-member RequiredCreateQty) independently; group complete only when both pass. |
| Decision | **Group scheduler + allocator (CONTRACT_A ≠ CONTRACT_B).** |
| Why | Fixes the 3500+4500→0+8000 bug where net-zero aggregate hid a required 3500 Create. |
| Impact | New `modCFGroupAllocator` (9 CFAlloc_* fns); scheduler gates `QtyReady` via `CFAlloc_IsContractBPass`; token rename `NO_QTY_WRITE`→`MEMBER_ALLOCATION_COMPLETE`. Verified G01 totCreate=3500. |

| Field | Value |
