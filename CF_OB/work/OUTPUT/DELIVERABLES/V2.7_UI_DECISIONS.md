# V2.7 UI DECISIONS

> The 4-button Control Center decisions, the macro bindings, and what remains cosmetic.
> Logic is DONE and self-tested; physical shape rearrangement on INPUT is deferred (last, per roadmap).

## 1. Button contract (4 buttons)

The sanctioned flow is a linear 4-step contract:

```
1. TẢI WH  →  2. CHECK  →  3. XỬ LÝ  →  4. LÀM MỚI
```

| # | Button label | Macro (OnAction) | Role |
|---|---|---|---|
| 1 | TẢI WH | `CF_LoadWH` | Load warehouse actuals (read side). |
| 2 | CHECK | `CF_CheckAndLoadPosting` | **Read-only** plan build; generates PlanID + fingerprints + lock cells. Never writes SAP. |
| 3 | XỬ LÝ | `CF_ExecutePlanToCFHandoff` | Executes ONLY a CHECK-locked, fingerprinted PlanID; stops at CF user handoff. |
| 4 | LÀM MỚI | `CF_ResetUI` | **New.** Invalidates the plan lock so no stale PlanID can execute; clears transient status; preserves history; `SAP_WRITE=0`. |

## 3. Why a distinct LÀM MỚI (reset) button

Without a reset, a user re-running CHECK after an aborted run could execute against a
**stale locked PlanID**. `CF_ResetUI` sets `PLAN!AJ2 = "RECHECK_REQUIRED_AFTER_RESET"`,
forcing a fresh CHECK before any execute. It is fail-safe:

- read-only against SAP (`SAP_WRITE=0`);
- never deletes RUN_HISTORY / RUN_LOG;
- never clears the user's typed OB list (INPUT col A) — only the derived status area.

`CFResetUI_SelfTest` = PASS (mutates then restores the lock cell; asserts the plan is
no longer LOCKED after reset).

## 4. State machine (intended)

| State | Buttons enabled |
|---|---|
| Fresh / after LÀM MỚI | 1. TẢI WH |
| WH loaded | 2. CHECK |
| CHECK locked (PlanID valid) | 3. XỬ LÝ, 4. LÀM MỚI |
| Executed / handoff | 4. LÀM MỚI |
| Stale lock detected | only 4. LÀM MỚI (forces re-CHECK) |

## 5. Worklist / status surface

- INPUT keeps the OB list on the left (col A); a small derived status area on the right (H1:N3) is what LÀM MỚI clears.
- Worklist columns (15) / editable columns (4) per REDESIGN remain a physical-layout task.
