### Issue #4: Bin-fill không group
**Question:** Khi tool "creat từng mã" cho phần điền bin, các mã đó có cùng vị trí nguồn (Source Bin) và lô (Batch) không?
**Answer:** **Khác vị trí hoặc lô**

**Analysis:**
- Materials are from DIFFERENT source bins or DIFFERENT batches
- **CONCLUSION: Issue #4 is NOT A BUG, it is CORRECT BEHAVIOR**
- LocationGroup definition: same Material + same SrcBin + same SrcBatch + same DstBin + same DstBatch
- If materials are from different bins/batches → different LocationGroups → must POST separately (SAP /SCWM/POST API limitation, cannot batch across different source bins)
- Each LocationGroup already batches all its members into ONE POST action with aggregate qty (code proven at modCodexWTRework.bas:14281-14284)

**User expectation mismatch:**
- User expects: "all materials in OB → 1 POST action"
- Reality: "each unique (src bin + batch) → 1 POST action"
- Example: 5 materials from 3 different bins → 3 POST actions (correct and unavoidable)

**MON check frequency:**
- User complaint: "check với mon khiến lâu hơn" (checking MON repeatedly makes it slower)
- Current behavior: MON verification happens AFTER EACH LocationGroup completes (safety requirement, cannot defer)
- Cannot eliminate this without breaking safety contract (must verify POST write succeeded before proceeding)

**ACTION:** Document this as expected behavior, explain to user that cross-bin batching is not possible

**Question:** Anh muốn tool chạy tuần tự theo kiểu nào?

**Analysis:**
- User wants: finish all cancels → then all bin-fills → then all creates
- **CURRENT BEHAVIOR ALREADY MATCHES THIS:**
  - Line 12925 in modCodexWTRework.bas: `"PHASE_ORDER=CANCEL_GROUP|LOCATION_GROUP|PRDO_DOCUMENT_GROUP|CREATE_GROUP|FINAL_VERIFY|CF_USER_HANDOFF"`
  - Line 15570: `"SCHEDULER_ORDER=CANCEL_GROUP|LOCATION_GROUP|PRDO_DOCUMENT_GROUP|CREATE_GROUP|FINAL_VERIFY|CF_GROUP|"`

- Example: within CANCEL_GROUP stage, if there are 5 QtyGroups, they process one after another, but log messages show group IDs → looks "nhảy lung tung" (jumping around)
- Solution: improve log formatting to make stage boundaries more visible

**ACTION:** Enhance logging to clearly demarcate stage boundaries, possibly add stage progress indicator ("CANCEL_GROUP: 3/5 groups completed")

### Issue #7: Group/map cần rộng hơn
**Question:** Anh muốn group thêm theo dimension nào?
**Answer:** **Group theo Material** (group by material across documents)

**Analysis:**
- User wants: same material across multiple documents → process together
- **CURRENT BEHAVIOR:** Each document has its own isolated QtyGroups/LocationGroups
  - QtyGroup key includes DocNo: `"QG|" & DocNo & "|" & Item & "|" & PlanID`
  - Material A in Doc 1 and Material A in Doc 2 → separate groups
- **REQUESTED BEHAVIOR:** Material A across all documents → 1 aggregate group

**Feasibility:**
- **TECHNICALLY POSSIBLE** but requires significant scheduler redesign
- Current scheduler builds groups per-document, then processes document-by-document
- Cross-document grouping would need:
  1. Global material-level grouping (not document-scoped)
  2. Handle mixed scenarios: same material but different src bins → still separate LocationGroups
  3. Cross-document cancel coordination (cancel all Doc A + Doc B members of Material X together)
  
**Trade-offs:**
- **BENEFIT:** Fewer total SAP actions (if same material in multiple docs, 1 cancel batch instead of N)
- **RISK:** More complex error recovery (if batch cancel fails, which document does it belong to?)
- **COMPLEXITY:** Medium-high (need to refactor group key generation + scheduler loops)

**Recommendation:**
- **DEFER to V2.9** — this is enhancement, not critical bug
- V2.8 focus: fix functional correctness issues (#2/#6 grid lazy-load)
- V2.9: redesign grouping to support cross-document material groups

**ACTION:** Document as enhancement request for V2.9
