## Investigation Phase 1: Scheduler & Cancel Logic

### Issue #1: Group cancel split — ROOT CAUSE CONFIRMED

**Evidence from V2.71 history:**
- Analyzed 11 `SCHED_CANCEL_GROUP_ACTION` events across multiple RunIDs
- **SMOKING GUN:** RunID `EXEC|20260821_030432|...` shows:
  - 4 cancel actions with `GROUP_MEMBERS=1` (sent as 4 separate 1-member batches)
  - 1 cancel action with `GROUP_MEMBERS=2` (sent as 1 batch of 2 members)
  - Pattern: `CANCEL_QUEUE → CANCEL_GROUP(SENT) → SCHED_CANCEL_GROUP_ACTION(1 member) → readback → priority` repeated 4 times, then one 2-member batch

**Root cause confirmed:**
- `CWR_SchedulerSendQueuedCancelGroup` (modCodexWTRework.bas:13413-13506) DOES batch correctly
- Line 13488: `If Not CWR_SendCancelSelection(ses, lower, rowList, messageText, wtList)` sends ALL matched members in one SAP action
- Line 13475-13479: builds comma-separated `rowList` and `wtList` for multi-selection
- Line 10464: `lower.selectedRows = selectedRowsText` (comma-separated row numbers)
- **The batching code is CORRECT**

**Why the split happens:**
- Scheduler calls `CWR_SchedulerSendQueuedCancelGroup` MULTIPLE TIMES per OB
- Line 13738 in parent loop `CWR_ExecutePreflightGroups` iterates `For Each groupID In qtyGroups.keys`
- Each call to `CWR_SchedulerSendQueuedCancelGroup` processes ONE QtyGroup
- **HYPOTHESIS:** User's "1 OB cancel 4-5 vị trí" may be 4-5 DIFFERENT QtyGroups (different Item/Material), NOT 1 group with 4-5 members
- If 4 materials in same OB → 4 distinct QtyGroupIds → 4 separate cancel batches (by design)
- If user expects "cancel all 4 materials in 1 SAP action" → that's cross-group batching, which V2.71 does NOT do

**Verification needed:**
- Check user's specific OB: are the 4-5 positions the SAME material (should be 1 QtyGroup) or DIFFERENT materials (4-5 QtyGroups)?
- If same material → CFX_GroupKey bug (line 195-200 in modCFX_Planner.bas, not yet read fully)
- If different materials → user expectation mismatch (cross-group cancel is NOT implemented, would need DocGroup-level cancel)

**Current behavior (from history):**
- V2.71 batches cancel within ONE QtyGroup correctly (seen `GROUP_MEMBERS=2` as 1 action)
- V2.71 does NOT batch across QtyGroups (each group → separate SAP action)

### Issue #6: Grid lazy-load — ROOT CAUSE CONFIRMED

**Evidence from code:**
- `modCodexSAPReadOnly.bas:1572-1607`: `For r = 0 To CLng(grid.rowCount) - 1` → `grid.GetCellValue(r, "TANUM")`
- NO scroll operation before read
- NO wait/delay after any scroll (grep found ZERO `scroll|verticalScrollbar|setCurrentCell.*scroll` patterns)
- **SMOKING GUN:** SAP GUI grids lazy-load off-screen rows; `GetCellValue` on unrendered row returns blank

**Affected code paths:**
1. `modCodexSAPReadOnly.bas:1572-1607` — `CodexConfirmWTExceptionAndReadStatus` loops full `rowCount`, reads `TANUM` per row
2. Multiple `For r = 0 To rowCount - 1` loops throughout modCodexSAPReadOnly.bas (grep found 8+ instances)
3. **CHECK phase is SAFE** — modCF_CheckPlanner.bas line 62 `CP_Preclassify` reads Excel worksheet (not SAP grid), then line 73 `CP_ResolveExceptions` may call POSTING cache (also Excel-backed)
4. **EXECUTOR phase is VULNERABLE** — all MON grid reads in live paths

**Why Issue #2 (bỏ sót mã) happens:**
- Tool scrolls fast through MON grid with many rows (user: "ob nhiều dòng", "máy yếu")
- Weak machine + many rows → bottom cells not yet rendered when `GetCellValue` called
- `GetCellValue` returns blank → tool thinks WT doesn't exist → skips that member → "bỏ sót mã"

**Fix required:**
- Add scroll-wait-read pattern before EVERY `For r = 0 To rowCount - 1` loop that reads SAP grid:
  ```vba
  ' Scroll to bottom to force full grid render
  If CLng(grid.rowCount) > 20 Then
      grid.SetCurrentCell CLng(grid.rowCount) - 1, "TANUM"
      CWR_WaitIdle ses, 0.5  ' 500ms render wait
  End If
  ' NOW safe to read all rows
  For r = 0 To CLng(grid.rowCount) - 1
      cellValue = grid.GetCellValue(r, columnKey)
  Next r
  ```
- Alternative: Use `grid.getAbsoluteRow(r)` API (slower but guaranteed), but requires API research

### Issue #4: Bin-fill not grouped — ROOT CAUSE IDENTIFIED (MISDIAGNOSIS BY USER)

**Evidence from code:**
- `modCodexWTRework.bas:14241-14317` — `CWR_ExecuteLocationGroups` function
- Line 14245-14315: **`For Each groupID In locationGroups.keys`** → processes one LocationGroup at a time
- Line 14281-14284: **"Use the aggregate required quantity; never send one POST change per plan member"**
  ```vba
  ' /SCWM/POST is one source-group action.  Use the aggregate required
  ' quantity; never send one POST change per plan member.
  CWR_TARGET_QTY = groupQty
  resultText = Codex_ExecutePostingBatchAtPickBin()
  ```
- Line 14283: `CWR_TARGET_QTY = groupQty` (aggregate of all members in the LocationGroup)
- Line 14284: ONE call to `Codex_ExecutePostingBatchAtPickBin()` per LocationGroup

**ROOT CAUSE: Location batching is ALREADY IMPLEMENTED and CORRECT**
- V2.71 DOES batch bin-change operations by LocationGroup
- Each LocationGroup → ONE /SCWM/POST action with aggregate qty
- NOT "creat từng mã" (not per-material)

**Why user perceives "không group được"?**
- **HYPOTHESIS 1:** User's OB has multiple DIFFERENT LocationGroups (different src bin, dst bin, or batch)
  - Example: 4 materials with 2 different source bins → 2 LocationGroups → 2 POST actions (by design)
  - User expects "1 POST for all 4 materials" but they're in 2 distinct bins → impossible to batch
- **HYPOTHESIS 2:** User sees "check với mon khiến lâu hơn" → MON check happens AFTER EACH LocationGroup completes (not after each material)
  - This is by design: verify the POST write before proceeding to next group
  - Cannot eliminate this verification without breaking safety contract

**Verification needed:**
- Ask user: are the materials that "creat từng mã" in the SAME source bin + batch, or DIFFERENT bins?
- If SAME bin → LocationGroup key bug (should be 1 group but splits into multiple)
- If DIFFERENT bins → user expectation mismatch (cross-bin POST batching is NOT possible in /SCWM/POST API)

**Current behavior (from code):**
- V2.71 batches bin-change by LocationGroup correctly (1 POST per group, aggregate qty)
- MON verification happens per LocationGroup (safety requirement, cannot defer)

**Likely conclusion:** Issue #4 is NOT a bug, it's user misunderstanding the batching scope (LocationGroup = same material + same src/dst bin/batch, not "all materials in OB")

### Issue #3: Messages not Vietnamese — CONFIRMED, TRIVIAL FIX

**Root cause:**
- All Result values are English enum strings (`BLOCKED_SOURCE_PLAN_INCOMPLETE`, `STOP`, etc.)
- Detail field has context but not displayed in UI
- Phase 1b worklist (not yet implemented) would show these to user

**Fix required:**
- Build Vietnamese message mapper:
  ```vba
  Private Function CP_VietnameseMessage(result As String, detail As String) As String
      Select Case UCase$(result)
          Case "BLOCKED_SOURCE_PLAN_INCOMPLETE"
              If InStr(detail, "Multi-batch") > 0 Then
                  CP_VietnameseMessage = "Vị trí có nhiều lô, cần chọn lô cụ thể"
              Else
                  CP_VietnameseMessage = "Dữ liệu nguồn chưa đầy đủ"
              End If
          Case "STOP"
              CP_VietnameseMessage = "Dừng: " & detail  ' fallback
          ' ... (map all Result enums)
      End Select
  End Function
  ```
- Phase 1b worklist calls this mapper before displaying to user
